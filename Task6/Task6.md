# Задание 6. Классификация данных

## 1. Концепция Data Classification Engine (C2)

Для обеспечения безопасности и соблюдения принципов Privacy by Design перед загрузкой данных в аналитическое хранилище внедряется **движок классификации данных**. Этот компонент автоматически анализирует входящие пакеты данных (Batch), определяет наличие чувствительной информации (PII, PHI, PCI) и маршрутизирует данные в соответствующие слои хранилища.

### Архитектура решения

Движок состоит из следующих компонентов:

1.  **Ingestion Service (ETL):** Принимает "сырые" данные из источников (Excel, 1C, PostgreSQL). Поскольку структура данных может меняться, этот слой не требует жесткой схемы на входе.
2.  **Classification Worker (Scanner):**
    *   **Schema Inference:** Определение текущей структуры данных (колонки, типы).
    *   **Pattern Matching:** Поиск паттернов по Regex (Email, Телефон, Паспорт РФ, СНИЛС).
    *   **NLP / NER (Named Entity Recognition):** Анализ контекста для выявления имен, диагнозов, адресов.
    *   **Sampling:** Для оптимизации сканируется не весь объем, а репрезентативная выборка (например, 1000 строк).
3.  **Policy Engine:** Применяет правила (например: "Если в колонке > 90% email-адресов -> Пометить как `Confidential`").
4.  **Metadata Store (Data Catalog):** Хранит результаты классификации (теги) и историю изменений схем.

## 2. Слои данных в аналитическом хранилище

Учитывая наличие конфиденциальных данных, хранилище (ClickHouse / S3 Data Lake) разделяется на изолированные зоны (Layers):

| Слой | Описание | Доступ | Шифрование |
| :--- | :--- | :--- | :--- |
| **Raw Layer (Landing)** | Данные "как есть". Используется для отладки загрузки и переклассификации. | Технический (ETL, Admins) | Полное шифрование (At Rest). Короткий срок хранения (TTL). |
| **Sensitive Layer (Core)** | Очищенные данные, содержащие PII/PHI. Используется для построения защищенных отчетов. | Ограниченный (Data Stewards, Compliance). | Column-level Encryption. Строгий RBAC. |
| **Anonymized Layer (Marts)** | Данные после маскирования/хэширования/агрегации. Основной слой для бизнес-аналитики. | Широкий (Analyst, BI Tools). | Не требуется (PII удалены). |

**Механизм загрузки:**
1.  Данные попадают в **Raw**.
2.  Classification Engine сканирует Raw.
3.  На основе тегов ETL-процесс:
    *   Копирует чувствительные данные в **Sensitive** (с шифрованием).
    *   Применяет функции анонимизации (hashing, masking) и загружает результат в **Anonymized**.

## 3. Метрики эффективности классификации

Для оценки качества работы движка используются следующие метрики:

1.  **Classification Coverage (%):** Доля колонок/таблиц, которым присвоен определенный класс (не `Unknown`).
    *   *Цель:* Минимизировать `Unknown`.
2.  **Confidence Score:** Средняя уверенность алгоритма в присвоенном классе.
    *   *Использование:* Если Score < 0.8, данные отправляются в "Карантин" для ручной разметки Data Steward'ом.
3.  **False Positive Rate (FPR):** Процент публичных данных, ошибочно помеченных как конфиденциальные.
    *   *Влияние:* Высокий FPR затрудняет работу аналитиков (нет доступа к данным).
4.  **False Negative Rate (FNR):** Процент чувствительных данных, пропущенных классификатором.
    *   *Влияние:* Критический риск утечки. Требует регулярного аудита.
5.  **Schema Drift Rate:** Частота изменений структуры входящих данных. Помогает понять, как часто нужно переобучать или настраивать правила.

## 4. Масштабируемость (Scalability)

При росте объема данных (Volume) и количества источников система масштабируется следующим образом:

1.  **Horizontal Scaling (Workers):** Компонент Classification Worker является stateless (без сохранения состояния). При увеличении нагрузки запускаются дополнительные реплики (Pods) в Kubernetes, которые параллельно обрабатывают разные батчи или партиции данных.
2.  **Sampling Strategy:** Вместо полного сканирования (Full Scan) используется статистическая выборка (Smart Sampling). Для определения типа данных в колонке на терабайт достаточно проанализировать несколько мегабайт случайных строк.
3.  **Metadata Caching:** Правила и теги кешируются (Redis) для быстрого доступа при потоковой обработке.
4.  **Separation of Compute & Storage:** Использование архитектуры (например, Spark + S3/ClickHouse), где вычислительные ресурсы для классификации масштабируются независимо от объема хранилища.
