# Задание 4. Оценка узких мест при миграции

## 1. Анализ ситуации: Миграция с монолита на микросервисы

Компания «Медикаменте» планирует кардинальную смену архитектуры: переход от локального монолита (Windows Server, Excel, 1С) к распределенной микросервисной системе (Kubernetes, Java, PostgreSQL, ClickHouse).

**Ключевые изменения и компоненты:**
*   **Инфраструктура:** Замена одного физического сервера на кластер Kubernetes (облачный или on-premise).
*   **Архитектура ПО:** Переход от файлового взаимодействия и OLE/COM к REST/gRPC API и асинхронным сообщениям.
*   **Данные:** Перенос неструктурированных данных (Excel) и реляционных данных (1С) в строго структурированные схемы PostgreSQL и колоночную ClickHouse.
*   **Процессы:** Внедрение CI/CD, автоматизированного тестирования и Infrastructure as Code (IaC) вместо ручного администрирования.

## 2. Диаграмма Исикавы (Причинно-следственная диаграмма)

Для выявления потенциальных причин узких мест и рисков миграции построена диаграмма «Рыбья кость».

**Файл диаграммы:** [medicamente-ishikawa.drawio](medicamente-ishikawa.drawio) (открыть в draw.io)

### Описание категорий рисков (Categories):

1.  **Персонал (People):**
    *   **Нехватка компетенций (DevOps/K8s):** Текущий штат (1 админ) не справится с поддержкой Kubernetes.
    *   **Сопротивление изменениям:** Сотрудники привыкли к Excel и могут саботировать новую систему.
    *   **Обучение:** Разработчикам нужно осваивать паттерны микросервисов (Circuit Breaker, Saga).

2.  **Инфраструктура (Infrastructure):**
    *   **Сложность эксплуатации K8s:** Риск неправильной настройки кластера, проблем с сетью и безопасностью.
    *   **Сетевые задержки (Latency):** Вызовы между сервисами по сети медленнее локальных вызовов в монолите.
    *   **Мониторинг:** Необходимо внедрять Distributed Tracing и централизованный логгинг (ELK), иначе диагностика невозможна.

3.  **Процессы (Process):**
    *   **Ручной деплой:** Старые методы не работают. Нужен надежный CI/CD пайплайн.
    *   **Тестирование (QA):** Сложность End-to-End тестирования распределенной системы.
    *   **Инцидент-менеджмент:** Нужны новые регламенты реакции на сбои (On-call дежурства).

4.  **Программное обеспечение (Software):**
    *   **Сложность микросервисов:** Риск создать "распределенный монолит" с высокой связностью.
    *   **CAP-теорема:** Обеспечение консистентности данных в распределенной системе (Distributed Transactions).
    *   **Legacy-код:** Сложности переноса бизнес-логики из 1С.

5.  **Данные (Data):**
    *   **Миграция (ETL):** Риск потери или искажения данных при переносе из "грязных" Excel-файлов.
    *   **Качество данных:** Необходимость очистки и нормализации данных перед загрузкой.
    *   **Защита (Privacy):** Новые требования к защите PII в распределенной среде (Task 2/3).

6.  **Интеграция (Integration):**
    *   **API Контракты:** Риск частых изменений контрактов (Breaking Changes), ломающих клиентов.
    *   **Внешние системы:** Нестабильность интеграции с лабораториями.

## 3. Рекомендации по устранению узких мест

На основе анализа предлагается план мероприятий по митигации рисков:

| Категория | Мера (Mitigation) | Приоритет |
| :--- | :--- | :--- |
| **Персонал** | **Найм/Аутстафф DevOps инженера** с опытом K8s для настройки инфраструктуры и обучения команды. | **High (Высокий)** |
| **Инфраструктура** | **Managed Kubernetes (Cloud):** Использование облачного K8s (Yandex Managed K8s и т.д.) для снижения эксплуатационной нагрузки на старте. | **High (Высокий)** |
| **Процессы** | **Внедрение CI/CD (GitLab CI/Jenkins):** Полная автоматизация сборки и деплоя с первого дня. | **High (Высокий)** |
| **Данные** | **Разработка ETL-скриптов с валидацией:** Создание промежуточного слоя (Staging) для очистки данных перед заливкой в Prod. | **High (Высокий)** |
| **ПО** | **Strangler Fig Pattern:** Постепенная миграция функционала (по одному сервису), а не Big Bang rewrite. | **Medium (Средний)** |
| **Мониторинг** | **Настройка Observability:** Внедрение Prometheus/Grafana и ELK до запуска в прод. | **Medium (Средний)** |
| **Интеграция** | **API Gateway & Versioning:** Использование шлюза (Kong/Nginx) и строгая политика версионирования API. | **Medium (Средний)** |
| **Персонал** | **Внутренние воркшопы:** Регулярное обучение сотрудников работе с новыми инструментами. | **Low (Низкий)** |
